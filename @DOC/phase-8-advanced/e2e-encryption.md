# 08. 종단간 암호화(E2E Encryption) — 추후 과제

> 참고: [토스 Gateway 아키텍처](https://toss.tech/article/22910)
> 지금 로드맵(`05-roadmap.md`) 범위에는 없음. Phase 7 심화 후보로만 남겨둔다.

## 1. 원문이 말하는 것

> "앱에서 암호화 키를 사용하여 요청 바디를 암호화하고 Gateway에서 이를 복호화 하여 서비스에 전달합니다."
> "복호화 과정에서 인증 / 인가 로직이 처리되고 복호화 된 데이터와 유저 정보를 서비스로 넘겨주게 됩니다."

**막으려는 위협**: 패킷 분석(네트워크 중간에서 요청 바디를 들여다보는 것). 금융 앱처럼 바디 안에 민감한 개인정보가 들어가는 경우, TLS만으로는 부족하다고 보고 앱-Gateway 사이에 애플리케이션 레벨 암호화를 한 겹 더 두는 개념이다.

## 2. 흐름

```
클라이언트(앱) ── 바디 암호화 ──▶ Gateway ── 복호화 + 인증/인가 ──▶ 업스트림 서비스
                                        (복호화된 데이터 + 유저 정보 전달)
```

- 암호화는 **클라이언트**가 함 (암호화 키를 이미 갖고 있다고 전제)
- 복호화는 **Gateway**가 함 — 그 시점에 인증/인가도 같이 처리
- 원문은 키 교환 방식이나 구체 알고리즘(AES 등)은 명시하지 않음. "매 요청을 서명할 아주 짧은 유효기간을 가진 안전한 키"라는 표현으로 봐서 단기 키를 쓰는 것 정도만 유추 가능

## 3. Dynamic Security와의 관계

원문에서 이 둘은 세트로 다뤄지지만 역할이 다르다:

| | 막는 것 | 방식 |
|---|---|---|
| **종단간 암호화** | 기밀성 (내용을 못 읽게) | 바디 암호화/복호화 |
| **Dynamic Security** | 무결성 + 출처 (변조 앱, 재전송/지연 공격) | 앱만 아는 값으로 요청마다 서명, 의심 요청은 FDS로 계정 비활성화까지 |

즉 암호화만 있으면 "내용은 못 보지만 그대로 재전송(replay)"은 막지 못하고, 서명만 있으면 "위변조는 막지만 내용은 그대로 노출"될 수 있어서 같이 쓴다.

## 4. 왜 지금 이 프로젝트에서는 스코프 아웃인가

이 패턴이 성립하려면 **"우리가 배포한, 우리가 신뢰하는 앱"** 이라는 경계가 있어야 한다. 토스처럼 자체 모바일 앱에 암호화 키/서명 로직을 심어두고, 그 앱만 유효한 요청을 만들 수 있게 하는 구조다.

이 프로젝트(`gateway-lab`)는 공공데이터포털류 **공개 API**를 실습 대상으로 한다 — 호출자는 우리가 배포한 앱이 아니라 제3의 개발자들이고, 애초에 "이 클라이언트는 변조되지 않았다"를 검증할 자체 앱이 없다. 그래서:

- 우리 쪽에서 표준화해야 하는 건 **누가 호출했는지(API Key → OAuth2/JWT)** 와 **얼마나 호출했는지(Rate Limit)** 이고, 이건 로드맵 Phase 2~4에서 이미 다룬다
- 앱 위변조/패킷 분석 방지는 애초에 대상이 다른 문제라 지금 로드맵에 넣지 않는다

## 5. 나중에 해본다면 필요한 것 (실습용 순서 초안)

실제로 만든다면 대략 이런 순서가 될 것이다. 지금 당장 할 일은 아니고, 방향만 적어둔다.

**클라이언트(가상의 "우리 앱") 측**
1. 암호화 키를 앱에 안전하게 심는 방법 결정 (하드코딩은 안 됨 — 키 교환/파생 필요)
2. 요청 바디 암호화 로직 (알고리즘 선택: AES-GCM 등)
3. Dynamic Security용 서명 생성 로직 (요청마다 짧은 유효기간의 키로 서명)

**Gateway 측**
1. 복호화 필터 추가 — 필터 체인에서 Sanitize/Passport 다음, 업스트림 호출 전
2. 키 관리 방식 결정 — Gateway가 직접 키를 들고 있을지, 별도 키 관리 서비스(KMS 유사)를 둘지
3. 서명 검증 필터 — 유효기간 만료/재전송(replay) 탐지 (예: 서명값 + timestamp를 Redis에 짧게 저장해서 재사용 탐지)
4. 의심 요청 처리 — 지금 있는 `GatewayException`/`GatewayErrorCode` 체계에 새 에러 코드 추가, 반복되면 별도 차단 로직(FDS와 유사한 역할)

**전제 조건**: 이걸 하려면 "우리 앱"이라는 실체가 있어야 하므로, 프로젝트에 클라이언트 앱(또는 앱을 흉내낼 테스트 클라이언트) 쪽 코드도 별도로 만들어야 한다 — 지금 `auth-server`/`developer-service`처럼 서버만 있는 구조로는 이 실습이 성립하지 않는다.
